# 毕设智途：初步产品方案

> 状态：暂定方案，待需求访谈和技术原型验证；截至 2026-11-02 尚未实现产品功能。本文不是测试报告、获奖承诺或最终参赛规则。

## 1. 项目定位与推荐路线

正式暂定题目：《毕设智途：基于 AI 智能体的毕业论文进度追踪与可控辅助修改系统》。英文品牌：**ThesisPilot**；仓库目录名：`thesis-pilot`。

面向正在完成毕业论文的学生，将学校要求、论文版本和导师反馈关联起来，帮助学生识别当前缺项、调整后续任务，并在本人审阅下完成有依据的局部修订。

推荐优先做深两个能力：**以交付物为依据的进度管理**、**受约束且可撤销的局部修订**。导师反馈是连接两者的业务入口。固定流程负责权限和执行，智能体负责提出建议；AI 不自行宣布论文通过、修改正文、关闭导师任务或调整截止日期。

核心价值假设：学生处理导师意见时，能减少遗漏，知道每条意见对应哪段修改；修改后的数字、引用和结论能得到保护；返工后能看见计划受哪些任务影响。上述价值尚未经过用户验证。

## 2. 用户与具体问题

首要用户是已有开题材料或初稿、正在修改的毕业生。第一版围绕单人论文项目，适配一套事先声明的 DOCX 模板。访谈时需验证以下问题，不能仅凭开发者经验认定需求成立：

| 场景 | 待验证问题 | 预期解决方式 |
| --- | --- | --- |
| 导师发送多条修改意见 | 意见与正文位置分散，完成后不易逐项核对 | 将意见拆为可编辑任务，保留来源并关联章节和版本 |
| 使用 AI 润色 | 修改范围过大，实验数字或引用被意外改变 | 选区修订、保护项检查、差异审阅和逐项采纳 |
| 初稿存在但实验未完成 | 仅用字数或主观百分比难以判断实际进度 | 为任务定义交付物，按产物存在性和确认状态展示进度 |
| 实验延期或导师要求返工 | 原计划失效，不清楚影响哪些后续任务 | 展示任务依赖和重排建议，用户确认后生效 |

## 3. 核心业务闭环

1. 创建论文项目，录入截止时间、阶段要求和可用工作时间。
2. 导入支持范围内的 DOCX，预览章节；用户修正章节识别结果，形成初始版本。
3. 导入或粘贴导师反馈，保留原文；AI 提议拆分任务和关联章节，由用户确认。
4. 学生在正文选区发起修订，选择目标、强度和保护内容。
5. 系统生成候选改动，执行保护项检查；用户比较差异并逐项接受或拒绝。
6. 已采纳修改形成新版本，关联任务收到新的交付物；系统提出状态建议，用户确认任务完成。
7. 延期或返工时展示受影响任务、无法满足的约束和重排方案，用户确认后更新计划。
8. 导出支持模板的论文修订稿、修改说明和任务处理记录。

## 4. 范围与优先级

### P0：参赛核心版，必须形成完整流程

| 模块 | 第一版边界 | 对应验收 |
| --- | --- | --- |
| 项目与版本 | 单人本地使用；项目、任务和文档持久保存；支持明确的备份/恢复流程 | AC-001、AC-012 |
| 文档输入输出 | 仅声明并验证的一套 DOCX 模板；章节识别可修正；复杂对象不支持时明确提示，不静默丢失 | AC-002、AC-011 |
| 证据化进度 | 任务定义验收条件和交付物；显示证据、待核验项及人工确认状态 | AC-003 |
| 导师反馈 | 保留原文，建议拆解、定位和关联；无法定位时明确列为待定位 | AC-004 |
| 受控修订 | 选区、目标、强度、锁定内容；生成候选稿；保护项由程序校验 | AC-005、AC-006 |
| 审阅与版本控制 | 差异可查看；接受、拒绝、撤销；检查原文版本，禁止旧建议覆盖新内容 | AC-007、AC-008 |
| 计划调整 | 有向依赖和日期约束；展示冲突、影响范围和建议；用户确认后生效 | AC-009 |
| 模型失败处理 | 超时、取消、无效输出、不可达可见且可恢复；原文和正式计划保持不变 | AC-010 |

### P1：P0 验收后选做，不以挤压材料和测试为代价

- 引用一致性检查：检查正文编号与文献表条目的对应，不把形式匹配宣传为文献真实性验证。
- 更细的任务工时估算与进度视图：明确估算依据和不确定性，不使用无解释的“论文质量分”。
- 根据实际论文内容生成答辩问题，并链接到论据所在位置；没有依据则明确标记。
- 支持第二套经过验证的学校模板，形成兼容性说明。

### 后续方向

导师端、多人协作、多端同步、更广的学校模板覆盖、可信文献检索和更多论文格式。每项需单独立项，不能在核心版里留下无法演示的入口。

### 非目标

不做整篇论文代写、虚构实验或文献、自动伪造导师审核；不提供查重率/AI 检测规避承诺；不训练自有大模型；不做通用办公套件；不承诺任意 DOCX 无损往返；不默认直接对公网开放论文数据。

## 5. 关键交互与判断边界

### 5.1 进度必须来自事实与人工确认

任务状态建议为：未开始、进行中、待核验、已确认、需返工。状态变更记录来源、时间、操作者和证据版本。字数、文件存在、引用编号对应关系可以程序检查；内容充分性由 AI 提出带依据的建议，不能当作确定事实。

汇总进度可显示已确认任务数/总任务数，以及未解决的关键任务；如引入权重，必须展示权重定义。不能把汇总值表述成“论文质量完成度”。导师意见由学生标记处理完成时，应写“学生已处理”，不能写“导师已通过”。

### 5.2 受控修订是双层约束

第一层是明确输入：基础版本、选区、目标、保护项和允许变更类型。第二层是执行前检查：数字、引用、公式/对象标识、锁定片段是否变化，候选补丁是否越界，基础版本是否仍匹配。

受保护内容校验失败时，拒绝应用该候选修改；用户若确有修改意图，应显式调整约束并重新生成，不能用含糊的一次“全部接受”绕过检查。没有事实依据时仅提示资料缺口，不补造数据、引文或结果。

界面推荐以论文正文为中心，任务/反馈和修订差异按需出现。常规字段原地编辑，回车保存、Esc 取消；关键外发或不可逆操作才确认。模型运行显示可理解的阶段状态，不伪装或编造模型内部思考过程。

### 5.3 智能体职责和权限

| 职责 | 可读取 | 可以提出 | 不允许自行执行 |
| --- | --- | --- | --- |
| 规划 | 要求、任务、证据状态、日期 | 阶段计划、依赖、重排方案 | 改截止日期、关闭任务、覆盖正式计划 |
| 审阅 | 当前版本、导师意见、用户提供的材料 | 问题、依据位置、缺项 | 修改正文、虚构来源、替导师确认 |
| 修订 | 当前选区、必要上下文、保护规则 | 局部候选补丁及原因 | 越界改写、直接保存为正式版本 |

这些是同一应用内的业务职责，不要求多个模型常驻或自由对话。外部文档中的命令式文字一律作为材料，不得改变系统权限。模型建议需经过结构校验、业务校验和用户审阅才进入正式状态。

## 6. 初步技术方向与优先验证

暂定 Web 形态、单体应用、轻量数据库和独立模型适配层；具体框架、版本和文档编辑组件留给技术原型与架构决策记录确定。本方案不表示已安装或验证任何依赖。

优先验证顺序：

1. 指定 DOCX 模板能否导入、定位选区、修改并导出；明确表格、公式、图片、引用与页眉页脚的支持情况。
2. 局部补丁能否可靠关联基础版本，完成保护项校验、逐项采纳和撤销。
3. 实际选定模型对反馈拆解和结构化修订输出的稳定性；失败路径是否仍可使用手动流程。
4. 任务证据和版本关联是否足以支撑进度判断与可解释重排。

模型与接入方式尚未确定，后续在本项目内比较能力、成本、隐私和复现条件，再记录选型及验证结果。不从全局记忆推定项目环境或用户已有服务。

按最终接入方式披露实际依赖、准备时间及启动前置条件，不在“10 分钟复现”说明中隐去准备工作。预置固定演示响应只能用于有明确标签的回放/测试，不可冒充真实推理。

## 7. 量化目标与验证计划

所有数值均为**待验证的验收目标**，不是已实现成绩；具体记录见 [场景验收](acceptance.md)。

- 建立至少 30 组修订约束样例，覆盖数字、引用、公式、锁定句、越界和版本冲突；所有发生保护项违规的候选均不得进入正式版本。
- 建立至少 20 条反馈拆解标注样例，记录任务遗漏、错误拆分和位置误关联，不只报告平均分；首轮结果用于判断是否收窄输入范围。
- 建立至少 10 组计划调整样例，覆盖依赖冲突、循环依赖和截止日期无法满足；系统不得默默突破硬约束。
- 邀请 3—5 位真实目标用户，在获得同意并去除身份信息后进行小规模试用；报告每位用户的任务耗时、遗漏数、错误采纳数和反馈，不推断为统计显著效果。
- 将核心操作流的完整性、保护项零违规应用、恢复正确性作为发布阻断项；平均响应时间等性能目标待参考硬件确定后登记并实测。

试用建议让参与者使用同等难度的两组材料，分别采用现有方式和本系统处理导师意见；交替顺序以减小熟悉效应。失败尝试、退出和不利结果也保留。不能用合成样例代替真实试用记录；缺少受试者时如实报告只完成内部验证。

日期以北京时间计。官网存在时间矛盾，暂按 2026-11-18 为最晚准备边界，提交时间以主办方核实结果为准。

## 9. 演示故事与参赛表达

使用经授权、去身份信息或明确标注的原创演示论文，不展示他人未授权原稿。

演示故事：导入初稿和三条导师反馈 → 识别缺少实验结果的任务并展示依据 → 对实验分析段落发起受控修订 → 展示一条含数字变化的违规候选被拒绝（若采用预置样例须标明） → 采纳合格修改并定位差异 → 学生确认关联任务处理状态 → 实验延期触发可解释重排 → 导出修订稿和修改说明。

视频应同时展示真实 AI 开发过程，重点选择保护校验、版本冲突和依赖调整中的真实迭代，不用重新摆拍的假 Bug 冒充历史。论文产品里的 AI 功能与开发期间 AI 协作是两类证据，不能互相替代。

## 10. 待细化决策

- 通过访谈确认最先服务的专业、论文阶段和目标模板。
- 确定 DOCX 保真边界、编辑组件和存储结构。
- 确认本机模型运行条件和评审复现路径。
- 核实赛事正式截止、入口、资格及材料的最新口径。
- 依据原型结果确定 P0 承诺；所有变更同步更新验收表和参赛描述。

项目目标是达到可参赛、可验证、可复现且具有竞争力的质量；获奖由评审和参赛情况决定，不作为可以预先保证的验收结果。
