# 多智能体任务登记与开工、开发、收工流程

状态：流程草案，可按本文执行；尚未安装为个人 Skill，尚未建立远端登记分支或自动互斥服务。适用于个人负责人使用多个 AI 开发会话，不改变赛事的个人参赛边界。

> 2026-11-16 起，本项目唯一状态台账改为 main 的 [施工单](construction-orders.md)，开工/收工遵循 [统一入口](construction-workflow.md)。下文 coordination 等方案仅作历史参考，不再作为本项目可选权威；所有权与冲突检查约束继续适用。

## 1. 采用什么机制

采用轻量任务登记，不要求每个功能递增产品版号。独立分支在修改前必须取得统一登记权威的认领确认，但不强制把登记写进 main。

| 协作方式 | 登记权威 | 何时可以开工 |
|---|---|---|
| 一个主会话统筹多个子智能体 | 主会话维护唯一台账，串行确认所有权 | 台账已保存，主会话已确认任务及文件范围 |
| 多个独立会话或机器 | 推荐远端 coordination 分支，固定一位协调者写入 | 协调者检查冲突后发布认领记录；开发者 fetch 并读到确认记录 |
| 团队已明确使用 main 台账 | 继续使用 main，无需迁移机制 | 登记提交进入远端 main，且确认无占用冲突 |

不要同时维护两份权威台账。切换模式时先停止新认领，迁移所有活跃任务，再公布唯一位置与协调者。只有本地未推送的记录不能协调独立机器；离线只能分析或继续已经确认且未变更范围的任务，不能新增认领。

`coordination` 只维护协调记录，不把其整条分支合入功能分支或 main。最终实现、验收与证据摘要随功能成果集成，main 上可保留流程说明和台账位置。每次任务开工不自动创建发布标签。

## 2. 编号与版本

| 字段 | 含义与规则 |
|---|---|
| task_id | 使用 `TASK-日期-UUID`；日期用于检索，UUID 避免各会话竞争递增号；由协调者检查重复 |
| base_commit | 实际读取的完整 Git SHA；分支名不能代替基线 |
| target_release | 已确认的目标版本或里程碑；未确定填“待定”，不得编造已有版本 |
| result_commits | 实际实现提交；尚未提交填“未提交”；rebase 后更新映射 |
| integration_commit | 实际集成到目标分支的提交；未集成不能填 done |
| migration / error_codes | 单独登记的共享资源；尚无迁移和错误码时填“不适用” |

产品发布版号由集成负责人统一确定。论文内容版本、候选建议基础版本与开发任务编号互不替代。

## 3. 开工

1. 读取仓库 AGENTS、README、赛事要求、产品验收、开发规范和已有证据；查看 Git 状态、当前分支和 HEAD。记录已有改动归属，不清理、重置或顺手提交。
2. 读取最新权威台账，确认唯一协调者。协调者暂时不可用时登记为“请求中”，不得自称已占用。
3. 按[登记模板](../evidence/templates/collaboration-task.md)写明功能、验收编号、文件范围、依赖、基线、分支/worktree 和验收命令。工程流程任务使用工程验收，不冒用产品 AC。
4. 协调者串行检查全部活跃任务的功能重叠、文件/目录包含关系、接口和共享资源；默认按整个文件分配所有权。两个不同文件也可能改动同一协议，必须检查语义依赖。
5. 认领通过后写入 owner、revision、确认时间和状态。跨会话模式须成功发布到权威远端；开发者获取最新记录再修改。
6. 优先使用独立分支和 worktree；不得切换共享主检出。共享目录只允许明确不重叠的编辑，Git 暂存、提交、rebase 等由协调者串行处理。worktree 隔离并不消除语义冲突。

公共文件（例如锁文件、全局路由、README、AGENTS、公共类型）指定一个整合者；开发者提交明确的变更需求，由整合者落地。数据库迁移与错误码集中分配；同时检查迁移父节点与多头问题，不只检查编号重复。

## 4. 登记一致性

每个任务使用一个独立记录；表格索引只是视图，以任务记录为准。协调者是台账唯一写入者，执行“读取最新记录 → 检查所有活跃占用 → 更新 revision → 发布 → 核实结果”的完整步骤。

远端拒绝更新时，重新 fetch/rebase 后必须重新检查所有权，不能只解决文本冲突就重试。即使两个任务改的是不同记录文件，也可能认领相同资源。没有发布成功的更新不生效。

本机制依靠单一协调者执行串行化，不声称 Markdown 或 Git 本身具有业务锁。协调者更换前须确认旧协调者停止写入并完成交接；无法确认时停止新认领。将来若允许多个协调者并发写入，应先实现事务式条件更新与冲突检查，再放宽此限制。

## 5. 开发

- 仅修改认领范围；扩大范围或变更接口时先申请更新，待协调者重新检查并确认后再编辑。
- 每个可验证里程碑、范围变化、阻塞、暂停和恢复都更新记录。默认长任务每 30 分钟报告一次进度；无需后台自动化，靠任务执行中的检查点落实。
- 超过约定更新时间只附加“待核实”标记，保留原状态和占用，不能自动释放或抢占。协调者收到旧执行者的停止确认，或由人类确认其进程已经终止后才可转交；记录确认依据、新 owner 和递增 revision。无法确认时保持阻塞。恢复的旧会话必须重读台账，发现已转交就停止写入并报告残留改动；revision 不是自动写入屏障。
- 定期对照基线与实际差异；发现未预期的同文件改动先停止该文件的编辑，保留双方工作并联系协调者。
- 保存真实输入输出定位、验证命令及结果、失败与复测；遵循[证据规范](../evidence/README.md)，不把原始私人对话、密钥或论文写入台账。

## 6. 收工与集成

| 状态 | 条件 | 占用处理 |
|---|---|---|
| requested | 申请尚未确认 | 不得开工 |
| active | 已确认并开发中 | 保留 |
| blocked / paused | 依赖阻塞或中断 | 默认保留，记录原因及下一步 |
| review | 实现完成，实际验证和交接齐全 | 保留至集成或明确转交 |
| integrated | 集成成功，目标分支复验通过 | 协调者记录集成提交后释放 |
| cancelled | 明确取消，残留改动已交接或隔离 | 协调者确认后释放，不自动删除文件 |

1. 开发者检查真实 diff，运行对应编译、类型检查、测试和核心流程；逐项写通过、失败或未执行。登记实际提交、证据位置、限制及交接说明。
2. 明确暂停还是完成待审；不得把“本轮结束”写成“已合并”。需求未满足时不能用“未执行”绕过完成门槛。
3. 集成者审阅任务范围与实际差异，显式暂存任务文件并检查暂存差异；不使用 `git add .` / `git add -A`，不覆盖他人未提交改动。
4. 推送前按[提交规范](../../CONTRIBUTING.md) fetch/rebase，并在最新目标基线上复验。检查迁移、错误码及接口兼容；不存在时记录“不适用”。发布部署仍遵循用户授权边界。
5. 只有确认成果进入目标分支、复验成功后才写 integrated 与实际 SHA，释放占用。已发布状态的核实以实际远端输出为准。
6. 不删除未合并分支、worktree 或残留文件；清理单独处理并遵循已有授权。

## 7. 后续 Skill 的执行接口

建议名称：`coordinate-development`；显示名：协同开发登记。

触发：用户要求多智能体协作、分支开工登记、任务认领、查看占用、开发进度、收工或恢复任务时使用。先读取项目规范和本文，再执行对应阶段，不额外建立第二份台账。

- “开工：实现某功能”：输出登记结果、负责人、基础提交、范围、状态与可执行验收；未确认认领不能执行实现。
- “开发：扩大某任务范围”：检查新占用及接口依赖，经协调者更新后继续。
- “收工：某任务”：核实实际改动和测试，将状态更新为暂停、阻塞或待审；仅集成者可确认已集成。
- “恢复：某任务”：读取最新 owner/revision、检查工作区和交接，确认仍有所有权后继续。
- “查看正在开发”：读取权威台账并列出功能、任务、负责人、基线/目标版本、范围、状态和最后更新时间。
